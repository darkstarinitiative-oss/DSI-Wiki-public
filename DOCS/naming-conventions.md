# DSI-Wiki — Project structure & naming conventions

This is the DSI standard project schema, applied here first. Every top-level directory below is
**mandatory** for a DSI-* project laid out this way; top-level directory names are UPPERCASE.

| Directory | Purpose |
|---|---|
| `CODE/` | The project's core functionality. |
| `TOOLS/` | Maintenance/setup/admin-level scripts and utilities. |
| `SKILLS/` | The functionality and CLI services the project exposes externally. |
| `DOCS/` | The documentation tree. |
| `JSONS/` | Project settings and other JSON files. |
| `DATA/` | Project-specific data sources, if any. |
| `SERVICES/` | Backups of the service-installation files for the project's service-running parts. |
| `STATUS.json` | Externally-readable control/health data. |
| `README.md` | Short project summary + what to know before setup. |
| `Requires.md` | Prerequisites needed to run. |

## `CODE/`

One subdirectory per architectural component, lowercase singular noun: `ingest/`, `gateway/`,
`mcpserver/`, `ui/`, `common/`.

Real entrypoint scripts keep the project's existing `DSI-Wiki-<Component>-<Role>.py` convention
(`DSI-Wiki-Ingest-Service-Class.py`, `DSI-Wiki-HTTP-Server.py`) — `.service` units and
`docker-compose.yml` reference these names directly. Internal library modules those entrypoints
import use plain `lowercase_snake_case.py` (`api_app.py`, `ollama_lock.py`).

**Two of these component names deliberately avoid an obvious choice, to prevent shadowing a
real Python package once `CODE/` is added to `sys.path`:**
- The HTTP/API/MCP/UI gateway lives at `CODE/gateway/`, not `CODE/http/` — Python's stdlib ships
  a real `http` package (used internally by `urllib`, `uvicorn`, `starlette`), and inserting
  `CODE/` onto `sys.path` (which every consumer of `common.ollama_lock` does) would put a local
  `CODE/http/` ahead of it, silently breaking anything downstream that does `import http`.
- The MCP tool server lives at `CODE/mcpserver/`, not `CODE/mcp/` — the project's own
  `requirements.txt` installs the real `mcp` SDK (`from mcp.server.fastmcp import FastMCP`), and
  a local `CODE/mcp/` on `sys.path` would shadow it the same way.

## `TOOLS/`

One file = one standalone admin operation, run directly (`python3 TOOLS/<name>.py`). Files keep
whatever name they already had when moved here (mix of `DSI-Wiki-<Verb>-<Noun>.py` for
established tools and `snake_case.py` for newer ones) — don't rename unless two collide.

## `SKILLS/`

One `SKILLS/<skill-name>/` directory per externally-exposed capability, kebab-case
(`dsi-wiki-read`, `dsi-wiki-internal-scan`, `dsi-wiki-provenance`), each containing `SKILL.md`.
The CLI implementations those skills (and the `~/.local/bin/DSI-wiki-*` wrappers) call live in
`SKILLS/cli/<verb>_<noun>.py`, snake_case (`wiki_get.py`, `wiki_search.py`).

## `JSONS/`

`JSONS/instances/<name>.json` — one per wiki instance; only `default.json` (an inert template)
is committed, real instances contain machine-specific paths and stay gitignored. Plus
`DSI-Wiki-HTTP-Config.json` (gateway config) and `DSI-Wiki-Multi-Server-Config.json` (generated
routing table — never hand-edited, regenerated by `TOOLS/DSI-Wiki-Service-Supervisor.py`).

## `SERVICES/`

Filenames are fixed by external convention, not free-form: systemd unit files must exactly
equal the installed unit name (`dsi-wiki-ingest.service`, `dsi-wiki-http.service` —
lowercase-hyphenated; an OS-level systemd requirement, not a style choice). Docker artifacts
keep their standard names (`Dockerfile`, `docker-compose.yml`, `.env.example`). `DEPLOY.md` is
the one prose file here.

## `DOCS/`

See the tree and per-file purpose in `README.md`'s Setup section and each file's own header.
